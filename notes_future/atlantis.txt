# Atlantis for Terraform Automation - Implementation Plan

## Concept Overview

Atlantis is a self-hosted application that automates Terraform workflows through Pull Requests. When you open a PR with Terraform changes, Atlantis automatically runs `terraform plan` and posts the results as a comment. You can then approve and apply changes directly from the PR by commenting `atlantis apply`. This provides GitOps-style automation for infrastructure changes with built-in review processes.

## Why Atlantis?

### Current Manual Process:
1. Developer modifies Terraform files locally
2. Runs `terraform plan` on their machine
3. Copy-pastes plan output to PR description
4. After approval, manually runs `terraform apply`
5. Risk of applying different changes than what was reviewed
6. No audit trail of who applied what

### With Atlantis:
1. Developer modifies Terraform files and opens PR
2. Atlantis automatically runs `terraform plan` and posts results
3. Team reviews the exact plan output in PR comments
4. After approval, comment `atlantis apply` to deploy
5. Atlantis applies the exact plan that was reviewed
6. Complete audit trail in GitHub PR history
7. Prevents drift between plan and apply

## How It Works - Step by Step

### Initial Setup:
1. Deploy Atlantis to Kubernetes cluster (EKS, not Minikube - requires public webhook access)
2. Configure GitHub webhook to send PR events to Atlantis
3. Create GitHub Personal Access Token with repo permissions
4. Store credentials as Sealed Secrets in Kubernetes
5. Configure AWS credentials via IRSA (IAM Roles for Service Accounts)
6. Add `atlantis.yaml` to vimex repository defining Terraform workflow

### When Developer Opens PR with Terraform Changes:
1. Developer modifies files in `vimex/terraform/` directory
2. Commits and pushes changes to feature branch
3. Opens Pull Request on GitHub
4. GitHub sends webhook to Atlantis LoadBalancer
5. Atlantis receives webhook, clones the repository
6. Detects changes in terraform directory
7. Automatically runs `terraform init` to initialize providers
8. Automatically runs `terraform plan` to show what will change
9. Comments on PR with: "atlantis plan" results
10. Posts plan output as PR comment with formatted diff
11. Locks the workspace to prevent concurrent modifications
12. Plan is stored and locked until apply or PR close

### Review Process:
1. Team reviews the plan output in PR comment
2. Can see exactly what resources will be created/modified/destroyed
3. Color-coded diff shows additions (green), changes (yellow), deletions (red)
4. Can request changes or approve based on plan
5. If code changes, Atlantis automatically reruns plan

### Applying Changes:
1. After PR approval, developer comments: `atlantis apply`
2. Atlantis verifies PR is approved and mergeable
3. Runs `terraform apply` with the locked plan file
4. Posts apply output as PR comment
5. Shows success or failure with detailed logs
6. Unlocks the workspace
7. Infrastructure changes are now deployed
8. Developer can then merge the PR (infrastructure already applied)

### Safety Features:
- Plan is locked until apply or PR close (prevents concurrent changes)
- Requires PR approval before allowing apply
- Apply uses exact plan file that was reviewed
- All commands and outputs logged in PR comments
- Can configure additional requirements (e.g., CODEOWNERS approval)

## Technical Components Needed

### 1. Atlantis Deployment (Kubernetes)

**Location:** vimex-gitops/gitops/helm/atlantis-helm-chart/

**Files to Create:**
- Chart.yaml - Helm chart metadata
- values.yaml - Configuration values
- templates/deployment.yaml - Atlantis pod definition
- templates/service.yaml - LoadBalancer service for webhooks
- templates/pvc.yaml - Persistent storage for Atlantis data
- templates/serviceaccount.yaml - K8s service account
- templates/rbac.yaml - RBAC permissions
- templates/sealed-secret.yaml - GitHub token and webhook secret
- templates/ingress.yaml - Optional ingress for custom domain

**Key Configuration:**
```
Image: ghcr.io/runatlantis/atlantis:v0.28.1
Service Type: LoadBalancer (for GitHub webhooks)
Environment Variables:
  - ATLANTIS_GH_USER: red512
  - ATLANTIS_GH_TOKEN: (from sealed secret)
  - ATLANTIS_GH_WEBHOOK_SECRET: (from sealed secret)
  - ATLANTIS_ATLANTIS_URL: LoadBalancer URL
  - ATLANTIS_REPO_ALLOWLIST: github.com/red512/*
Resources:
  - CPU: 100m-1000m
  - Memory: 256Mi-1Gi
  - Storage: 5Gi PVC for plans
```

### 2. ArgoCD Application

**Location:** vimex-gitops/gitops/apps/atlantis.yaml

**Content:**
```
Deploys atlantis-helm-chart
Target namespace: atlantis
Auto-sync enabled
Creates namespace automatically
```

### 3. Repository Configuration

**Location:** vimex/atlantis.yaml

**Content:**
```
Defines Terraform workflow for vimex repository
Specifies terraform directory location
Sets Terraform version (1.6.0)
Configures autoplan on .tf file changes
Requires PR approval before apply
Custom workflow steps if needed
```

### 4. Sealed Secrets

**Secrets Needed:**
- GitHub Personal Access Token (repo permissions, webhook management)
- Webhook secret (random string for validating GitHub requests)
- AWS credentials (optional, prefer IRSA)

**Create with:**
```bash
kubectl create secret generic atlantis-github-secret \
  -n atlantis \
  --from-literal=token=<github_token> \
  --from-literal=webhook-secret=<random_secret> \
  --dry-run=client -o yaml | \
kubeseal --format yaml > sealed-secret.yaml
```

### 5. GitHub Webhook Configuration

**Setup in GitHub Repository Settings:**
```
URL: https://<atlantis-loadbalancer>/events
Content-Type: application/json
Secret: (same as sealed secret)
Events:
  - Pull requests
  - Issue comments
  - Pull request reviews
  - Pull request review comments
  - Pushes
```

### 6. AWS IAM Role (IRSA)

**For Terraform to manage AWS resources:**
```
Create IAM role: atlantis-terraform-role
Attach policies: AdministratorAccess (or more restrictive)
Configure trust relationship with EKS OIDC provider
Annotate service account with role ARN
```

- Credentials stored securely in Kubernetes
- No credentials on developer machines
- AWS access via IRSA (temporary credentials)

## Security Considerations

### Network Security:
- Atlantis needs public LoadBalancer for GitHub webhooks
- Use webhook secret to validate requests from GitHub
- Consider IP allowlisting if GitHub Enterprise
- TLS/HTTPS required for production

### Credentials:
- GitHub token stored as Sealed Secret
- AWS credentials via IRSA (no static keys)
- Webhook secret validates GitHub requests
- Rotate secrets regularly

### Access Control:
- Only allowed repositories can use Atlantis
- Requires PR approval before apply
- GitHub branch protection rules enforced
- Can require specific reviewers (CODEOWNERS)
- RBAC limits Atlantis pod permissions

### Terraform State:
- State stored in S3 with encryption
- State locking via DynamoDB
- Versioning enabled on S3 bucket
- Access limited to Atlantis IAM role

## Atlantis vs Minikube - Important Note

### Why Atlantis Doesn't Work with Minikube:

**Problem 1: GitHub Webhooks**
- GitHub needs to send webhooks to Atlantis when PRs are created/updated
- Minikube runs locally on your machine (localhost)
- GitHub cannot reach localhost addresses
- Webhooks would fail with "connection refused"

**Problem 2: Public URL Required**
- Atlantis needs a publicly accessible URL
- Format: https://your-atlantis-url.com/events
- Minikube only has local cluster IP (e.g., 192.168.49.2)
- No public DNS or LoadBalancer

**Workarounds (Development Only):**

Option A: ngrok tunnel
- Run: ngrok http 4141
- Get temporary URL: https://abc123.ngrok.io
- Configure GitHub webhook with ngrok URL
- Issues: URL changes on restart, not production-ready

Option B: Cloudflare Tunnel
- More stable than ngrok
- Can use custom domain
- Still not recommended for production

**Recommended Approach:**
- Deploy Atlantis to existing EKS cluster
- Use AWS LoadBalancer for public access
- Production-ready and secure
- Already have infrastructure in place

## Example User Journey

### Developer Workflow:
1. Clone vimex repository
2. Create branch: terraform/add-s3-bucket
3. Modify: vimex/terraform/s3-bucket.tf
4. Add new S3 bucket resource
5. Commit: "feat: add logging bucket"
6. Push: git push origin terraform/add-s3-bucket
7. Open PR on GitHub
8. Within 30 seconds, Atlantis comments with plan:
   ```
   Ran Plan for dir: terraform workspace: default
   
   Terraform will perform the following actions:
   
   + aws_s3_bucket.logs
       bucket = "vimex-logs-2025"
       acl    = "private"
   
   Plan: 1 to add, 0 to change, 0 to destroy
   ```
9. Team reviews plan in PR
10. Approves PR
10. Developer comments: atlantis apply
11. Atlantis runs terraform apply and comments with results:
    ```
    Ran Apply for dir: terraform workspace: default
    
    aws_s3_bucket.logs: Creating...
    aws_s3_bucket.logs: Creation complete after 2s
    
    Apply complete! Resources: 1 added, 0 changed, 0 destroyed.
    ```
12. Infrastructure is now deployed to AWS
13. Verify changes work as expected
14. Merge PR to main (infrastructure already applied)

## Monitoring and Debugging

### Check Atlantis Status:
```bash
# Pod status
kubectl get pods -n atlantis

# View logs
kubectl logs -n atlantis deployment/atlantis -f

# Check service and LoadBalancer
kubectl get svc -n atlantis

# Get LoadBalancer URL
kubectl get svc atlantis -n atlantis -o jsonpath='{.status.loadBalancer.ingress[0].hostname}'
```

### Verify GitHub Webhook:
```
Go to: https://github.com/red512/vimex/settings/hooks
Click on webhook
View "Recent Deliveries"
Check response codes (200 = success)
View payload and response
```

### Common Issues:

**Webhook not triggering:**
- Check webhook secret matches sealed secret
- Verify LoadBalancer is accessible from internet
- Check Atlantis logs for incoming requests
- Verify GitHub token has correct permissions

**Plan fails:**
- Check AWS credentials/IRSA configuration
- Verify Terraform state backend is accessible
- Check S3 bucket and DynamoDB table exist
- Review Terraform version compatibility

**Apply not allowed:**
- Verify PR is approved
- Check apply_requirements in atlantis.yaml
- Ensure branch is up to date
- Verify no merge conflicts

**Permission denied:**
- Check IAM role has sufficient permissions
- Verify IRSA annotation on service account
- Check trust relationship with OIDC provider
- Review CloudTrail for denied API calls
